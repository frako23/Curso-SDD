# Curso SDD

Repositorio de material práctico para trabajar con desarrollo guiado por
especificaciones (Spec-Driven Development, SDD). Contiene prompts, plantillas,
convenciones y ejemplos de flujo para crear productos nuevos, documentar
sistemas heredados, coordinar trabajo en paralelo y modernizar módulos sin
perder el comportamiento existente.

Este repositorio es documental: no contiene una aplicación ejecutable ni el
código de los productos descritos en los ejemplos.

## Recorridos recomendados

### Crear un producto nuevo

1. Leer [`spec-first/001-prompt_constitution.txt`](<spec-first/001-prompt_constitution.txt>) y fijar los principios del producto.
2. Usar [`spec-first/002-preguntas_spec.txt`](<spec-first/002-preguntas_spec.txt>) como lista de revisión.
3. Redactar la primera especificación a partir de [`spec-first/003-spec_plantilla_universal.txt`](<spec-first/003-spec_plantilla_universal.txt>) y [`spec-first/004-prompt_spec_servilleta.txt`](<spec-first/004-prompt_spec_servilleta.txt>).
4. Resolver ambigüedades antes de implementar con [`spec-first/005-prompt_speckit_specify.txt`](<spec-first/005-prompt_speckit_specify.txt>).
5. Continuar con el plan, la inicialización del repositorio y la documentación técnica según los prompts 006–014.

### Documentar un sistema heredado

Seguir [`reverse-specs/001-prompt_constitution.txt`](<reverse-specs/001-prompt_constitution.txt>) y después el flujo de reconocimiento: mapa del sistema, ciclo de vida de factura, riesgos, memoria histórica, reglas de negocio, contradicciones y anomalías. A continuación, cerrar las decisiones con la entrevista, congelar el comportamiento mediante tests, proponer la partición por dominios y ensamblar el paquete final.

### Coordinar varias features

La carpeta [`trabajo en paralelo/`](<trabajo en paralelo>) muestra un flujo con una spec base, features independientes en ramas, revisión cruzada desde el tronco y posterior integración. [`trabajo en paralelo/004-prompt_revision_specs.txt`](<trabajo en paralelo/004-prompt_revision_specs.txt>) define cómo leer las specs por commit sin hacer checkout.

### Modernizar sin cambiar el contrato

Usar [`modernización guiada/002-prompt_analisis_modulos.txt`](<modernización guiada/002-prompt_analisis_modulos.txt>) para elegir el primer módulo, [`modernización guiada/003-prompt_spec_modernizacion_motor_calculo.txt`](<modernización guiada/003-prompt_spec_modernizacion_motor_calculo.txt>) para extraerlo manteniendo equivalencia y [`modernización guiada/004-prompt_cambio_anomalia.txt`](<modernización guiada/004-prompt_cambio_anomalia.txt>) para aplicar después un cambio de negocio explícito y no retroactivo.

## Principios comunes

- La especificación es la fuente de verdad del comportamiento observable.
- El alcance debe ser explícito; las ideas nuevas se registran como propuestas.
- Las reglas de negocio se expresan con ejemplos concretos y criterios verificables.
- En sistemas heredados, el comportamiento actual se documenta y protege antes de corregirse.
- Toda afirmación importante debe tener evidencia: código, datos, tests o decisión del negocio.
- Las specs se organizan por dominio de negocio, no por fichero o capa técnica.
- Los cambios de comportamiento se realizan mediante decisiones documentadas y deltas, no de forma implícita.
- El material está redactado principalmente en español de España; los ejemplos fijan también sus propios idiomas, monedas y contextos.

## Estado y alcance

- Hay 48 archivos fuente: 47 prompts/configuraciones y 1 skill con sus metadatos e instrucciones, además de este README. El inventario se compone de archivos `.txt`, `.yaml` y `.md`.
- No hay código de producción, dependencias instalables, comandos de arranque ni suite de tests para ejecutar en este repositorio.
- Los comandos `/speckit-*` y `/opsx:*` son instrucciones para el flujo de trabajo de especificación; no son scripts locales incluidos aquí.
- Los documentos describen proyectos de ejemplo distintos. No deben interpretarse como una única aplicación ni como un contrato técnico común.

## Observaciones para quien use el material

Algunos prompts son deliberadamente borradores o ejercicios y contienen decisiones abiertas, erratas o tensiones que deben resolverse durante la especificación. Por ejemplo, el material de PresupuestosPro mezcla en distintos puntos euro/dólar y España/Venezuela, y deja preguntas sobre redondeo, logo y primer uso. Esas inconsistencias son parte del ejercicio: deben detectarse con las preguntas de clarificación antes de construir.

## Herramientas mencionadas

La documentación hace referencia a Git, GitHub Spec Kit, OpenSpec y worktrees. La referencia completa y actualizada de GitHub Spec Kit está en [`github spec kit/github spec kit.md`](<github spec kit/github spec kit.md>) e incluye comandos de terminal, comandos del agente para Codex, el flujo SDD, extensiones de bugs e ideas, integraciones, presets, workflows y bundles.

La secuencia mínima de inicialización es:

```text
specify init --here --force --integration codex
specify extension add git
```

La skill de [`spec-audit`](<SKILLs/spec-audit/SKILL.md>) es solo de auditoría: informa sobre divergencias entre especificaciones y código, pero no corrige specs, código ni tests.

# Especificación: PresupuestosPro v0

## 1. Objetivo y contexto de negocio

PresupuestosPro es una herramienta para que un freelancer venezolano cree presupuestos profesionales con su marca y los descargue en PDF para enviárselos a sus clientes, sin pelearse con Excel ni con plantillas.

Hoy, la escena real es esta: son las once de la noche, un cliente ha pedido precio y hay que mandárselo mañana. El freelancer abre una hoja de cálculo vieja, copia un presupuesto anterior, cambia los conceptos a mano, calcula con la calculadora del móvil y cruza los dedos para que los números cuadren. El resultado tarda demasiado y se ve poco profesional.

Éxito de negocio: poder emitir un presupuesto correcto y con buena imagen en menos de 5 minutos.

## 2. Usuarios

- **El freelancer (usa la aplicación).** trabajador autónomo de Venezuela (diseñador, programador, fotógrafo, consultor…). Trabaja solo, no es técnico y hace varios presupuestos al mes. Sabe manejarse con una web normal; no sabe (ni quiere saber) de impuestos más allá de lo justo.
- **El cliente (no usa la aplicación).** Recibe el PDF por email. Puede ser una **empresa o autónomo**, o un **particular**.

## 3. Escenarios de usuario

- HU1 — Como freelancer, quiero configurar mi nombre, datos de contacto y logo, para que mis presupuestos salgan con mi marca sin tener que ponerla cada vez.
- HU2 — Como freelancer, quiero mantener un catálogo de mis servicios con un precio por defecto cada uno, para no reescribir lo mismo en cada presupuesto.
- HU3 — Como freelancer, quiero crear un presupuesto eligiendo el cliente y añadiendo líneas (de mi catálogo o escritas a mano), para adaptarlo a cada encargo.
- HU4 — Como freelancer, quiero que la base imponible, el IVA, la retención de IRPF (cuando toque) y el total se calculen solos, para no equivocarme con los impuestos.
- HU5 — Como freelancer, quiero descargar el presupuesto como PDF con mi logo, número y validez, para enviárselo al cliente con buena imagen.

## 4. Requisitos funcionales

- RF1. El sistema debe permitir guardar y editar el perfil del freelancer: nombre, datos de contacto y logo.
- RF2. El sistema debe permitir crear, editar y eliminar servicios del catálogo, cada uno con nombre y precio por defecto.
- RF3. El sistema debe permitir crear un presupuesto indicando los datos del cliente y su tipo: **empresa/autónomo** o **particular**.
- RF4. Cada línea del presupuesto debe poder venir del catálogo o escribirse a mano, con descripción, cantidad y precio unitario.
- RF5. El sistema debe calcular automáticamente, en cada presupuesto:
  - Base imponible = suma de (cantidad × precio unitario) de todas las líneas.
  - subtotal y totalizar al final, dar precio en Dólares tomando la data del banco central de venezuela
- RF7. El sistema debe numerar los presupuestos automáticamente con el formato AAAA-NNN (por ejemplo, 2026-001), reiniciando el contador cada año.
- RF8. El presupuesto debe mostrar la fecha de emisión y una validez de 30 días desde esa fecha.
- RF9. El sistema debe permitir editar o eliminar cualquier línea del presupuesto antes de generar el PDF.
- RF10. El sistema debe generar un PDF con el logo, los datos del freelancer y del cliente, el número, las fechas, la tabla de líneas y el desglose de base, IVA, retención y total.
- RF11. Cuando el freelancer vuelva a abrir la aplicación, su perfil, su catálogo y sus presupuestos deben seguir ahí.

## 5. Reglas de negocio (con ejemplo)

- **Fórmula del total:** Total = sumatoria de subtotales
- **Numeración:** formato AAAA-NNN (2026-001, 2026-002…), reinicia cada año.
- **Validez:** 30 días desde la fecha de emisión.

**Ejemplo de referencia (debe cuadrar al céntimo):**

| Concepto | Importe |
|---|---|
| Diseño de página web | $ 1.500,00 |
| Sesión de fotos de producto | $ 500,00  |
| **Total a pagar** | ** $ 2.00,00 ** |

## 6. Criterios de aceptación (verificables sin código)

- CA1. El total mostrado es exactamente $ 2.000,00.
- CA2. El segundo presupuesto creado en el año recibe automáticamente el número siguiente (por ejemplo, 2026-002).
- CA3. El PDF descargado muestra el logo, el número, la fecha de emisión, la validez y el desglose completo.
- CA4. Puedo editar o borrar cualquier línea antes de generar el PDF y los totales se actualizan.
- CA5. Cierro la aplicación, la vuelvo a abrir, y mi perfil, mi catálogo y mis presupuestos siguen ahí.

## 7. Casos límite

- CL1. Presupuesto sin ninguna línea: no se genera el PDF; se avisa al freelancer.
- CL2. Línea escrita a mano, fuera del catálogo: permitida (no todo encargo está catalogado).
- CL3. Cliente particular con la retención activada por error: la retención no se aplica (manda el tipo de cliente).

## 8. Fuera de alcance (v0)

- Sin cuentas de usuario ni "entrar con contraseña".
- Sin guardar nada en la nube: los datos viven en el ordenador del freelancer.
- Sin multidivisa: solo Dólares.
- Sin enviar el PDF por email desde la aplicación (el freelancer lo descarga y lo manda él).
- Sin descuentos por línea ni globales (si algún día se añaden, se especificarán con su regla de cálculo y ejemplos).

---

## 9. Preguntas abiertas (para la sesión de clarificación con Spec Kit)

Cosas que sé que no he decidido. No las escondo: las apunto para resolverlas en el siguiente paso.

- PA1. **Logo:** ¿qué aparece en el PDF si el freelancer todavía no ha subido logo?
- PA2. **Numeración:** ¿se puede corregir un número a mano si hace falta, o es intocable?
- PA3. **Redondeo:** ¿cómo se redondean exactamente los importes con decimales raros ( $ 2,345)?
- PA4. **Primer uso:** ¿qué ve el freelancer la primera vez, con el catálogo vacío y sin perfil?
- PA5. **Cambio de ordenador:** si los datos viven en este ordenador, ¿qué pasa si uso otro? ¿Lo asumimos y lo decimos claramente?

- RF9. El sistema debe permitir editar o eliminar cualquier línea del presupuesto antes de generar el PDF.
- RF10. El sistema debe generar un PDF con el logo, los datos del freelancer y del cliente, el número, las fechas, la tabla de líneas y el desglose de base, IVA, retención y total.
- RF11. Cuando el freelancer vuelva a abrir la aplicación, su perfil, su catálogo y sus presupuestos deben seguir ahí.

## 5. Reglas de negocio (con ejemplo)

- **Fórmula del total:** Total = sumatoria de subtotales
- **Numeración:** formato AAAA-NNN (2026-001, 2026-002…), reinicia cada año.
- **Validez:** 30 días desde la fecha de emisión.

## 6. Criterios de aceptación (verificables sin código)

- CA1. El total mostrado es exactamente $ 2.000,00.
- CA2. El segundo presupuesto creado en el año recibe automáticamente el número siguiente (por ejemplo, 2026-002).
- CA3. El PDF descargado muestra el logo, el número, la fecha de emisión, la validez y el desglose completo.
- CA4. Puedo editar o borrar cualquier línea antes de generar el PDF y los totales se actualizan.
- CA5. Cierro la aplicación, la vuelvo a abrir, y mi perfil, mi catálogo y mis presupuestos siguen ahí.

## 7. Casos límite

- CL1. Presupuesto sin ninguna línea: no se genera el PDF; se avisa al freelancer.
- CL2. Línea escrita a mano, fuera del catálogo: permitida (no todo encargo está catalogado).
- CL3. Cliente particular con la retención activada por error: la retención no se aplica (manda el tipo de cliente).

## 8. Fuera de alcance (v0)

- Sin cuentas de usuario ni "entrar con contraseña".
- Sin guardar nada en la nube: los datos viven en el ordenador del freelancer.
- Sin multidivisa: solo Dólares.
- Sin enviar el PDF por email desde la aplicación (el freelancer lo descarga y lo manda él).

# Exportar todos mis presupuestos en un .zip

## Objetivo
Que el freelancer pueda llevarse TODOS sus presupuestos de una sola vez, en un único
archivo comprimido .zip, como copia de seguridad y para archivarlos donde quiera.
Hoy sus datos viven solo en su navegador (decisión de la constitution): si formatea
el ordenador, cambia de navegador o borra el historial, lo pierde todo. Este botón
es su seguro de vida.

## Usuario
El mismo freelancer de siempre: autónomo, no técnico. Sabe descargar un archivo y
descomprimir un .zip con doble clic. No sabe (ni tiene por qué saber) qué hay dentro
de un "archivo de datos".

## Alcance
- Un botón "Exportar todo (.zip)" en un lugar visible de la lista de presupuestos.
- Al pulsarlo se descarga UN único archivo .zip que contiene:
  - Un PDF por cada presupuesto existente, exactamente el mismo PDF que ya genera
    la app para ese presupuesto.
  - Un único archivo de datos con toda la información (presupuestos, catálogo de
    servicios y perfil del freelancer, logo incluido), pensado para poder restaurar
    la aplicación en el futuro.
- Funciona con los datos que haya: 1 presupuesto o 200.

## Reglas de negocio
- Nombre del .zip: "presupuestospro-copia-AAAA-MM-DD.zip", con la fecha del día de
  la exportación. Ejemplo: exporto el 15/03/2026 → presupuestospro-copia-2026-03-15.zip.
- Nombre de cada PDF dentro del zip: número + cliente. Ejemplo: "2026-001 - Estudio
  García.pdf".
- La exportación NO modifica nada: es solo lectura. Después de exportar, la app
  sigue exactamente igual.
- Los PDF del zip deben cuadrar al céntimo con los que genera la app uno a uno
  (mismo ejemplo de control del Módulo 2: total 3.604,00 €).

## Criterios de éxito
- Con 3 presupuestos creados, pulso el botón y descargo un único .zip.
- Al descomprimirlo veo 3 PDF con nombre "número - cliente" y un archivo de datos.
- Abro cualquiera de los PDF y es idéntico al que descargo desde la app para ese
  mismo presupuesto.
- Con 0 presupuestos, el botón avisa de que no hay nada que exportar (y no se
  descarga ningún zip vacío).

## Casos límite
- Sin presupuestos: aviso claro, sin descarga.
- Cliente con caracteres conflictivos en el nombre ("Diseño/Web S.L."): el nombre de
  archivo se limpia para que el zip no se rompa.
- Muchos presupuestos (50+): puede tardar; tiene que verse que está trabajando.

## Fuera de alcance
- IMPORTAR la copia (restaurar los datos): será otra spec, otro capítulo.
- Exportar a Excel/CSV con formato contable.
- Copias automáticas o programadas: solo bajo demanda, con su botón.
- Enviar el zip por email o subirlo a ninguna nube.

- La carta se organiza en categorías definidas por el dueño (desayunos,

- La carta muestra todos los platos activos de cada categoría. Un plato
  "activo" es un plato que el dueño no ha eliminado del catálogo; los
  platos eliminados no aparecen jamás, pero se conservan archivados en el
  sistema (los pedidos históricos los referencian).

  y de forma visible en todos los platos, con los 14 alérgenos de
  declaración obligatoria de la normativa europea; un plato sin alérgenos
  declara explícitamente "sin alérgenos" (la ausencia de información no es
  una opción legal).
- La carta es pública: no requiere identificación para consultarse, y
  carga en menos de 2 segundos en un móvil de gama media con 4G.
- El dueño gestiona el catálogo (crear, editar, archivar platos y
  categorías, subir fotos con límite de tamaño) desde una pantalla de
  administración protegida con la sesión de establecimiento, pensada para
  usarse desde un móvil.

de cuenta o registro del cliente final (prohibido por el principio 3

# GitHub Spec Kit
# Referencia de comandos, significados y usos

Actualizado: 2026-10-01

## 1. Diferencia entre tipos de comandos

Spec Kit tiene dos familias de comandos:

1. Comandos de terminal: empiezan por specify y se ejecutan en PowerShell,
   Bash o cualquier terminal compatible.
2. Comandos del agente: son habilidades que se invocan en el chat del agente
   de programación. No se ejecutan como comandos de terminal.

Formas habituales de invocar una habilidad del agente:

- GitHub Copilot en modo skills: /speckit-specify
- Codex, Command Code y ZCode: $speckit-specify
- Kimi: /skill:speckit-specify
- Notación usada en la documentación: /speckit.specify

En este documento se usa $speckit-* para los ejemplos del agente Codex. La
forma exacta depende de la integración seleccionada al ejecutar specify init.

Notación:

- <valor>: argumento obligatorio.
- [valor]: argumento opcional.
- --opcion: opción o indicador.
- slug: identificador corto en minúsculas y con guiones, por ejemplo
  login-crash.

## 2. Instalación y comprobación inicial

Requisitos principales: Python 3.11 o superior, uv y un agente de
programación compatible.

    uv tool install specify-cli

Instala el ejecutable specify de forma persistente.

    uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z

Instala una versión concreta desde una etiqueta del repositorio. Sustituir
vX.Y.Z por una etiqueta real, conservando la v inicial.

    pipx install specify-cli
    pip install specify-cli

Alternativas de instalación mediante pipx o pip.

    specify --version
    specify -V

Muestran rápidamente la versión del CLI instalada.

    specify version
    specify version --features
    specify version --features --json

Muestran la versión de Spec Kit, Python, plataforma y arquitectura. La opción
--features informa las capacidades disponibles; --json produce una salida
para scripts y agentes.

    specify check

Comprueba localmente si están disponibles las herramientas CLI de los agentes.
La comprobación es offline.

## 3. Crear o inicializar un proyecto

    specify init [<nombre-proyecto>]

Crea un proyecto Spec Kit con la estructura .specify/, plantillas, scripts e
integración con el agente de programación.

Ejemplos:

    specify init my-project --integration codex
    cd my-project

    specify init --here --integration codex
    specify init --here --force --integration codex

- my-project: crea una carpeta nueva con ese nombre.
- --here: inicializa en la carpeta actual.
- --force: permite combinar la infraestructura de Spec Kit con una carpeta
  existente y omite la confirmación de combinación.
- --integration <key>: selecciona el agente, por ejemplo codex, copilot,
  claude o gemini.

Opciones de specify init:

    specify init my-project --integration codex --script ps
    specify init my-project --integration codex --ignore-agent-tools
    specify init my-project --integration codex --non-interactive
    specify init my-project --integration codex --preset <preset-id>
    specify init my-project --integration generic --integration-options="--commands-dir .myagent/cmds"

- --script sh: instala scripts Bash/Zsh.
- --script ps: instala scripts PowerShell; es la opción habitual en Windows.
- --script py: instala scripts Python.
- --ignore-agent-tools: no comprueba si el ejecutable del agente está
  instalado localmente.
- --non-interactive: evita preguntas interactivas, útil en CI.
- --preset <preset-id>: instala un preset durante la inicialización.
- --integration-options: pasa opciones específicas a la integración.

La inicialización de Git y la creación de ramas pertenecen a la extensión
opcional git; Spec Kit no la instala automáticamente.

## 4. Actualizar el CLI y los archivos del proyecto

    specify self check

Comprueba si existe una versión más reciente del CLI. Es una operación de solo
lectura.

    specify self upgrade
    specify self upgrade --dry-run
    specify self upgrade --tag vX.Y.Z

- self upgrade: actualiza el CLI instalado mediante uv tool o pipx.
- --dry-run: muestra lo que haría sin modificar la instalación.
- --tag: actualiza a una etiqueta específica.

    specify integration status
    specify integration upgrade <key>
    specify extension update

Después de actualizar el CLI, estos comandos refrescan los archivos de la
integración y las extensiones instaladas en el proyecto.

## 5. Integraciones con agentes

Las integraciones generan los archivos y carpetas que el agente necesita para
reconocer las habilidades de Spec Kit. Todas las operaciones de gestión de
integraciones se ejecutan dentro de un proyecto inicializado.

    specify integration list
    specify integration list --catalog

Lista las integraciones integradas, las instaladas y, con --catalog, las que
pueden descubrirse en los catálogos.

    specify integration search [query]
    specify integration info <integration-id>

- search: busca integraciones disponibles; admite --tag y --author.
- info: muestra descripción, autor, licencia, etiquetas, origen y estado.

    specify integration install <key>
    specify integration uninstall [<key>]
    specify integration switch <key>
    specify integration use <key>
    specify integration upgrade [<key>]
    specify integration status
    specify integration status --json

- install: instala una integración adicional.
- uninstall: elimina una integración; --force también elimina archivos
  modificados.
- switch: cambia a otra integración, instalándola si hace falta.
- use: selecciona como predeterminada una integración ya instalada.
- upgrade: actualiza sus archivos y comandos.
- status: informa integraciones instaladas, archivos faltantes o modificados;
  --json sirve para CI y scripts.

Opciones importantes:

    specify integration install generic --integration-options="--commands-dir .myagent/cmds"
    specify integration install generic --integration-options="--commands-dir .myagent/skills --skills"
    specify integration install <key> --force
    specify integration switch <key> --refresh-shared-infra
    specify integration scaffold <key>

- --integration-options: opciones específicas, como la carpeta de comandos.
- --skills: usa carpetas speckit-<nombre>/SKILL.md cuando la integración
  lo admite.
- --force: permite instalar junto a integraciones no declaradas como seguras
  para múltiples instalaciones o sobrescribir archivos gestionados.
- --refresh-shared-infra: refresca también la infraestructura compartida.
- scaffold: crea una integración mínima para desarrolladores de Spec Kit.

Catálogos de integraciones:

    specify integration catalog list
    specify integration catalog add <url> [--name <nombre>]
    specify integration catalog remove <index>

Permiten consultar, agregar o quitar fuentes de descubrimiento de
integraciones.

## 6. Extensiones

Las extensiones agregan comandos, plantillas, scripts, hooks o procesos
especializados. Requieren que el proyecto haya sido inicializado.

    specify extension search [query]

Busca extensiones disponibles. Admite --tag, --author y --verified.

    specify extension add <name>
    specify extension add <name> --version <version>
    specify extension add <name> --dev <directorio>
    specify extension add <name> --from <url>
    specify extension add <name> --priority <N>

Instala una extensión desde un catálogo, una versión concreta, un directorio
local o una URL. Un número de prioridad menor tiene precedencia mayor cuando
varias extensiones ofrecen el mismo comando.

Extensiones de procesos oficiales:

    specify extension add git
    specify extension add bug
    specify extension add assess
    specify extension add github

- git: ramas, inicialización y commits automáticos.
- bug: diagnóstico, reparación y prueba de bugs.
- assess: evaluación de ideas antes de invertir en su desarrollo.
- github: reemplazo con namespace para la sincronización de tareas con
  GitHub; puede exponer taskstoissues como speckit.github.taskstoissues.

Gestión de extensiones:

    specify extension list
    specify extension list --available
    specify extension list --all
    specify extension list --json
    specify extension info <name>
    specify extension info <name> --versions
    specify extension update [<name>]
    specify extension enable <name>
    specify extension disable <name>
    specify extension set-priority <name> <priority>
    specify extension remove <name>
    specify extension remove <name> --keep-config
    specify extension remove <name> --force

- list: muestra extensiones instaladas; --available agrega las no
  instaladas, --all muestra ambas y --json genera salida estructurada.
- info: muestra metadatos, comandos, configuración y versiones disponibles.
- update: actualiza una extensión o todas si no se indica un nombre.
- enable / disable: activa o desactiva una extensión sin desinstalarla.
- set-priority: cambia su prioridad de resolución.
- remove: elimina una extensión; --keep-config conserva la configuración y
  --force omite la confirmación.

Catálogos de extensiones:

    specify extension catalog list
    specify extension catalog add <url> --name <name>
    specify extension catalog remove <name>

Una fuente discovery-only permite descubrir, pero no instalar directamente,
su contenido. Revisar siempre una extensión de terceros antes de instalarla.

- search: busca presets.

## 9. Workflows

Los workflows automatizan varios pasos, prompts, comandos, scripts de shell y
aprobaciones humanas en una secuencia reutilizable.

    specify workflow run <source>
    specify workflow run speckit -i spec="Build a kanban board"
    specify workflow run <archivo.yml> --json

Ejecuta un workflow identificado por catálogo, URL o archivo local. -i o
--input pasa valores como clave=valor; --json devuelve el resultado para
automatización.

    specify workflow resume <run-id>
    specify workflow resume <run-id> --input <clave>=<valor>
    specify workflow resume <run-id> --json

Reanuda un workflow pausado o fallido desde el paso exacto donde se detuvo.

    specify workflow status [<run-id>]
    specify workflow status [<run-id>] --json
    specify workflow list

- status: muestra el estado de una ejecución o de todas las ejecuciones.
- Estados: created, running, completed, paused, failed y aborted.
- list: lista los workflows instalados.

Gestión de workflows:

    specify workflow add <source>
    specify workflow add <source> --dev
    specify workflow add <workflow-id> --from <url>
    specify workflow add <workflow-id> --version <version>
    specify workflow update [<workflow-id>]
    specify workflow enable <workflow-id>
    specify workflow disable <workflow-id>
    specify workflow remove <workflow-id>
    specify workflow search [query]
    specify workflow info <workflow-id>
    specify workflow info <workflow-id> --versions
    specify workflow resolve <workflow-id>

- add: instala un workflow desde catálogo, URL, YAML, directorio o archivo
  comprimido.
- --dev: instala una fuente local durante el desarrollo.
- update: actualiza uno o todos los workflows instalados.
- enable / disable: activa o desactiva un workflow sin eliminarlo.
- remove: desinstala un workflow.
- search: busca workflows por texto, --tag o --author.
- info: muestra pasos, entradas, requisitos y versiones.
- resolve: muestra cómo se compone el workflow a partir de la base y sus
  overlays.

Overlays de workflows:

    specify workflow overlay add <archivo-overlay.yml> --priority <N>
    specify workflow overlay list <workflow-id>
    specify workflow overlay set-priority <workflow-id> <overlay-id> <N>
    specify workflow overlay enable <workflow-id> <overlay-id>
    specify workflow overlay disable <workflow-id> <overlay-id>
    specify workflow overlay remove <workflow-id> <overlay-id>

Permiten insertar, reemplazar o quitar pasos de un workflow sin editar el
workflow instalado. Los números de prioridad menores tienen precedencia mayor.

Catálogos de workflows:

    specify workflow catalog list
    specify workflow catalog add <url> [--name <name>]
    specify workflow catalog remove <index>

### Tipos de paso de workflow

Las versiones que incluyen catálogo de pasos también exponen:

    specify workflow step list

    specify workflow step info <id>
    specify workflow step catalog list

Estos comandos descubren, instalan, consultan o eliminan tipos de paso

## 10. Bundles

Un bundle empaqueta extensiones, presets, workflows y pasos en una unidad
versionada e instalable.

    specify bundle search [query]
    specify bundle search [query] --offline
    specify bundle search [query] --json
    specify bundle info <bundle-id>
    specify bundle info <bundle-id> --offline --json

- search: busca bundles disponibles.
- --offline: evita la red.
- --json: produce salida estructurada.
- info: muestra todos los componentes y versiones que instalaría.

    specify bundle install <bundle-id | path>
    specify bundle add <bundle-id>

- install y add: instalan un bundle desde un catálogo, directorio, archivo

## 11. Flujo principal de Spec-Driven Development (SDD)

Después de specify init, abrir el agente dentro de la carpeta del proyecto.
El flujo recomendado es:

    $speckit-constitution
    $speckit-specify
    $speckit-clarify
    $speckit-plan
    $speckit-checklist
    $speckit-tasks
    $speckit-analyze
    $speckit-implement
    $speckit-converge

Solo specify es estrictamente necesario antes de plan. clarify, checklist y
analyze son controles de calidad opcionales.

### $speckit-constitution

    $speckit-constitution Define principles focused on code quality, testing and maintainability.

Crea o actualiza la constitución del proyecto: principios que guían y evalúan
las fases posteriores. Normalmente se ejecuta una vez por proyecto.

### $speckit-specify

    $speckit-specify Build a photo organizer with albums grouped by date.

Crea o actualiza la especificación funcional. Define qué se necesita y por qué,
incluyendo comportamiento visible para el usuario, historias de usuario y
criterios de aceptación; no decide todavía la tecnología.

### $speckit-clarify

    $speckit-clarify Focus on permissions, status changes and assignment rules.

Formula preguntas sobre ambigüedades de la especificación y registra las
respuestas en spec.md. Puede repetirse antes de planificar.

### $speckit-plan

    $speckit-plan Use Vite, vanilla JavaScript and SQLite for local metadata.

Genera el plan técnico: arquitectura, tecnologías, datos, interfaces,
restricciones y estrategia de implementación.

### $speckit-checklist

    $speckit-checklist
    $speckit-checklist Focus on authentication and authorization requirements.

Genera una lista de comprobación de calidad de los requisitos. Verifica que la
especificación sea completa, clara, consistente y no ambigua. No es una lista
de tareas de implementación.

### $speckit-tasks

    $speckit-tasks

Convierte los artefactos de diseño en tasks.md: tareas accionables ordenadas
por dependencias, fases e historias de usuario.

### $speckit-analyze

    $speckit-analyze

Realiza un análisis de solo lectura entre spec.md, plan.md y tasks.md.
Detecta conflictos, huecos, ambigüedades y tareas sin requisito asociado. No
edita archivos.

### $speckit-implement

    $speckit-implement
    $speckit-implement Implement only the Setup and Foundational phases.

Ejecuta las tareas de tasks.md respetando sus dependencias y marcas de
paralelización. Puede ejecutarse por fases pasando un alcance como argumento.

### $speckit-converge

    $speckit-converge

Compara la implementación con la especificación, el plan y las tareas. Si no
hay faltantes informa Converged; si encuentra faltantes, agrega nuevas tareas
en la sección Convergence de tasks.md. Repetir implement y converge hasta
obtener Converged.

### $speckit-taskstoissues

    $speckit-taskstoissues

Convierte las tareas existentes en issues de GitHub. Requiere un remoto origin,
acceso al repositorio y herramientas MCP de GitHub. Es opcional y no es
necesario para implementar o converger.

La extensión GitHub también puede proporcionar la variante namespaced:

    specify extension add github
    $speckit-github-taskstoissues

## 12. Corrección de bugs

Instalar primero la extensión:

    specify extension add bug

Flujo del agente:

    $speckit-bug-assess "Submitting an empty password crashes the login form." slug=login-crash
    $speckit-bug-fix slug=login-crash
    $speckit-bug-test slug=login-crash

- $speckit-bug-assess: evalúa si el reporte es un bug real, localiza las
  rutas de código y propone una corrección. Solo escribe assessment.md.
- $speckit-bug-fix: aplica la corrección evaluada y documenta los cambios en
  fix.md. Es el único comando de este flujo que modifica el código fuente.
- $speckit-bug-test: reproduce y verifica el resultado; escribe test.md.

Los reportes se guardan en .specify/bugs/<slug>/. El veredicto final es
verified, partial o failed. Un bug sin verificación no debe considerarse
corregido.

## 13. Evaluación de ideas

Instalar primero la extensión:

    specify extension add assess

Flujo del agente:

    $speckit-assess-intake "Let users work offline and sync when they reconnect." slug=offline-mode
    $speckit-assess-research slug=offline-mode
    $speckit-assess-define slug=offline-mode
    $speckit-assess-shape slug=offline-mode
    $speckit-assess-decide slug=offline-mode

- $speckit-assess-intake: captura la idea desde texto, URL, ticket o
  referencia a un código y crea intake.md.
- $speckit-assess-research: reúne evidencia a favor y en contra, con fuentes
  y nivel de confianza; crea research.md.
- $speckit-assess-define: define usuarios, problema, objetivos, no-objetivos,
  métricas y coste de no actuar; crea problem.md.
- $speckit-assess-shape: compara opciones conceptuales, esfuerzo y
  compromisos; crea concept.md.
- $speckit-assess-decide: registra scorecard, justificación y veredicto en
  decision.md.

Los artefactos se guardan en .specify/assessments/<slug>/. Los veredictos son:

- go: la idea tiene evidencia suficiente y una opción recomendada.
- needs-clarification: existen incertidumbres que bloquean la decisión.
- kill: no conviene continuar por ahora; se documenta la razón.

Una decisión go puede entregarse después a $speckit-specify, pero la evaluación
no inicia SDD automáticamente.

## 14. Extensión Git

Instalación:

    specify extension add git

Comandos del agente que proporciona la extensión:

    $speckit-git-initialize
    $speckit-git-feature
    $speckit-git-validate
    $speckit-git-remote
    $speckit-git-commit

- git-initialize: inicializa un repositorio Git con un mensaje de commit
  configurable.
- git-feature: crea una rama de feature con numeración secuencial o por
  fecha/hora.
- git-validate: comprueba que la rama actual respete la convención de nombres.
- git-remote: detecta la URL remota para integraciones con GitHub.
- git-commit: crea commits automáticos según la configuración.

La extensión puede ejecutar hooks antes o después de comandos SDD, por ejemplo
crear el repositorio antes de constitution, crear una rama antes de specify y
hacer commits después de plan, tasks o implement.

Configuración principal:

    .specify/extensions/git/git-config.yml

La extensión Git es opcional. Si Git no está instalado, Spec Kit puede seguir
creando especificaciones, aunque las ramas, validaciones y remotos se omiten
con una advertencia.

Actúa como **auditor de sincronía entre especificaciones y código** del proyecto CartaYa. Tu único objetivo es detectar **spec drift**: divergencias entre lo que dicen las especificaciones vivas y lo que hace el código real. **No arregles nada; solo audita e informa.**

## Fuentes de verdad a comparar

- **Especificaciones vivas**: `openspec/specs/**/spec.md` (todas las capacidades). Son la fuente de verdad vigente.
- **Convenciones y principios**: `openspec/config.yaml` (campos `context` y `rules`).
- **Cambios activos**: `openspec/changes/` (excluida `archive/`). Un cambio activo es **intención declarada, NO drift**; pero señala cambios activos rancios (implementados y sin archivar, o abandonados) como hallazgos de **PROCESO**.
- **Historial archivado**: `openspec/changes/archive/` (como contexto de _por qué_ existen los requisitos; **no** como fuente de verdad vigente).
- **Código**: `src/` (servidor y web) y esquema de base de datos.
- **Tests**: `tests/`.
- **Historial reciente**: `git log` de los últimos 30 días como pista de cambios que puedan no estar reflejados en specs.

## Procedimiento

Antes de empezar, carga todas las fuentes:

1. Lee `openspec/config.yaml` (campos `context` y `rules`).
2. Lee todos los `openspec/specs/**/spec.md`.
3. Lista `openspec/changes/` (identifica cuáles son activos vs `archive/`).
4. Localiza el esquema de base de datos y recorre `src/` y `tests/`.
5. Ejecuta `git log --since="30 days ago" --oneline --stat` para localizar zonas modificadas recientemente.

Realiza la auditoría en **las dos direcciones**:

### DIRECCIÓN 1 — ¿El código cumple las specs vivas? (CÓDIGO→SPEC)

Para cada requisito y escenario de cada capacidad, verifica **leyendo el código** si sigue implementado tal y como está descrito. Presta especial atención a:

- estados y transiciones,
- validaciones,
- reglas numéricas (umbrales, límites, cantidades),
- textos visibles para el usuario.

### DIRECCIÓN 2 — ¿Las specs vivas describen el código? (SPEC→CÓDIGO)

Recorre el comportamiento observable del código (endpoints, pantallas, validaciones, estados, columnas de base de datos con significado de negocio) y localiza funcionalidad que **ninguna spec viva mencione** o que **contradiga** lo especificado. Usa el `git log` reciente para priorizar zonas modificadas.

### Comprobaciones adicionales

- **Drift de ENTORNO**: afirmaciones técnicas del `context` de `config.yaml` o de los `design` de cambios recientes que ya no sean ciertas (versiones, librerías, decisiones de arquitectura).
- **Drift de TESTS**: escenarios sin test asociado, y tests que validen comportamiento que ya no está especificado.
- **Drift SEMÁNTICO**: términos de las specs usados en el código o en specs de otras capacidades con un significado distinto al definido.

## Criterio de severidad

- **alta**: afecta a dinero, pedidos o disponibilidad de platos.
- **media**: afecta a la experiencia visible del cliente.
- **baja**: es interno o cosmético.

**Sé conservador**: ante la duda entre "cumple" y "drift", marca **drift con severidad baja** y explica la duda.

## Formato del informe (Markdown)

1. **Veredicto global en una línea**: `SINCRONIZADO` / `DRIFT LEVE` / `DRIFT GRAVE`.

2. **Tabla de hallazgos** con columnas:

   | ID  | Tipo | Severidad | Capacidad y requisito | Evidencia | Descripción |
   | --- | ---- | --------- | --------------------- | --------- | ----------- |
   - **Tipo**: `CÓDIGO→SPEC` | `SPEC→CÓDIGO` | `ENTORNO` | `TESTS` | `SEMÁNTICO` | `PROCESO`
   - **Severidad**: alta / media / baja
   - **Evidencia**: fichero y líneas, o commit
   - **Descripción**: en una frase

3. **Para cada hallazgo, una recomendación de resolución**, eligiendo entre:
   - **(a) actualizar la spec** porque el comportamiento del código es el deseado (vía cambio de regularización de OpenSpec),
   - **(b) corregir el código** porque la spec describe el comportamiento deseado,
   - **(c) escalar a decisión de negocio** porque no es evidente cuál de los dos es el deseado.

   Justifica la elección en **una frase** y **NO apliques ninguna**.

4. **Lista de zonas que no has podido verificar** y por qué.
